## 0. 一句话结论

> **现有门限 `expectedAmplitude × 0.5 × bodyScale` 在姿态主链路上不会挡掉真实动作。** 在推荐站位（人占画面高 45%~75%）下，真人动作信号的 3.5s 窗峰峰值是门限的 **1.7×~5.5×**；真实引擎端到端实测，姿态链路 **被门限挡下的帧数 = 0**。
> `0.5` 系数与 `bodyScale` 公式**不建议改动**（它们是姿态链路防"关键点抖动漏计数"的关键，实测支撑）。
> 唯一可选的低风险调整：把 `bodyScale` 的**下限从 1.0 放宽到 ~0.6**，为"孩子站得比推荐距离更远"留余量（数据见 §4.3）。**开合跳是四类动作里余量最小的一类，值得单独盯。**

## 1. 测量方法

### 1.1 为什么必须用真实动作视频，而不是合成人形

项目已确证：**MediaPipe 对合成方块人返回 0 关键点**，只有真照片/真人视频能出 33 点。所以：

1. 用 cv2 把项目自带真人动作视频逐帧抽成 jpg（原分辨率宽 512）；
2. 页面内用**生产同款** `new Pose({modelComplexity:0, smoothLandmarks:true, minDetectionConfidence:0.5, minTrackingConfidence:0.5})` 逐帧推理；
3. 经**生产同款** `PoseVision.mapLandmarks()` 得到引擎意义下的 `width / height / centroidY`；
4. 用真实 `MotionEngine.createEngine()` 跑姿态主链路与掩码链路，读 `getState().reps / repGate / repSpread`。

> 关键：`detectReps()` 的闸门比的是 **`signalWindow(key, 3.5)` 的峰峰值**（最近 3.5 秒），不是整段范围。所以本报告主用 **「3.5s 滑动窗峰峰值」的中位/分位**，与引擎逐帧判定完全同构；「整段范围」只作参考。

## 3. 两链路对照

### 3.1 `width` 信号：姿态链路 **不小于** 掩码链路，反而更大

| 量 | 掩码链路（受控合成人形，真实引擎实测 `_exp-series.json`） | 姿态链路（真人，本次实测） |
|---|---|---|
| 开合跳 width 峰峰 @人高≈0.77 | 0.146 | **0.282** |
| 开合跳 width 峰峰 @人高≈0.39 | 0.083 | ≈0.14（k=2.0 插值） |
| 静止噪声 width 峰峰 @2m | 0.031 | — |
| 静止噪声 width 峰峰 @4m | 0.063 | — |
| 静止抖动地板（等价量级） | — | j=0.016 → 0.042；j≈0.013 → 0.035 |

**在相近人形尺寸（人高≈0.77）下，姿态链路 width 峰峰值 ≈ 掩码链路的 1.9 倍。** 原因直白：掩码链路的 `width` 是**背景差前景框**（受阈值、残影、背景学习率影响，手臂上举时框会缩），而姿态链路的 `width` 是 **33 关键点的 min/max 外接框**（张开的手臂/腿直接反映到边界，不丢）。

→ **团队担心"姿态链路信号更小 → 门限偏严"的方向，对 `width` 不成立：姿态链路信号更大。**

### 3.2 `centroidY` / `height`：两链路量级相当

| 量 | 掩码链路（受控合成人形） | 姿态链路（真人） |
|---|---|---|
| 半蹲 centroidY 峰峰 @人高≈0.86 | 0.221 | — |
| 深蹲 centroidY 3.5s窗峰峰 @人高≈0.66 | — | 0.181 |
| 静止噪声 centroidY 峰峰 @2m / @4m | 0.018 / 0.038 | — |

量级同阶（0.18~0.22），姿态链路略小但远高于门限。

### 3.3 掩码链路在真实动作视频上没有有效参照（如实说明）

用真实动作视频夹跑引擎掩码链路时，`width` 峰峰值 = 0、reps = 0（表 2-5）。原因是这批视频是**剪辑过的宣传素材**（相机非静止、背景本身在动、人占比大），背景差法拿不到稳定人形。因此 **§3.1 的两链路定量对照以项目既有的「受控合成人形」数据为准**，而不是拿这批视频的掩码输出当参照 —— 那会是错误结论。（`build/_maskchain-ref.py` 的输出同样被这一点污染，仅存档、不作结论依据。）

## 4. 结论与建议值

### 4.1 回答 Q1：姿态链路绝对值与波动

- `live.width`：典型 **0.12~0.27**；动作 3.5s 窗峰峰 **0.043（跳绳）~0.282（开合跳）**。
- `live.height`：典型 **0.43~0.77**；峰峰 **0.059~0.610**（波比跳最大，因为它整体趴下/起立）。
- `live.centroidY`：典型 **0.53~0.69**；峰峰 **0.043~0.330**。
- 与掩码链路对比：`width` 姿态 **≈1.9×** 掩码（同尺寸）；`centroidY`/`height` 基本同阶。**不是"更小"，而是"同阶或更大"。**

### 4.2 回答 Q2：现有门限会不会挡掉真实动作？

**正常站位（人占画面高 45%~75%，即站立校准的推荐区）下：不会。**

- 真人动作 3.5s 窗峰峰 / 门限 = **1.71×（跳绳最小）~5.48×（半蹲热身）**。
- 真实引擎姿态主链路端到端：**被门限挡下的帧 = 0/408~413**。
- 位置衰减：把人缩到 k=1.0~2.6（人高 0.77→0.26）仍在门限之上；**只有开合跳在 k=3.4（人高 0.227，远于推荐站位）时会掉到 0.88×**。

→ **"孩子跳了却不计数"在正常站位下不是这道门限造成的。** 若真机仍出现，优先排查：
1. **孩子手臂没举过头** → 开合跳的 `width` 增量主要来自"手臂上举 + 双脚打开"，手臂若贴身，width 波动会显著缩到门限附近（表 2-3 的远距离行给出了同类缩幅的参照：width 峰峰可跌到 0.08~0.12）。这属于设计意图（动作不标准不算），**但必须在 UI 上给"手臂再举高一点 / 双脚再打开一点"的实时提示**，否则孩子会以为系统瞎了；
2. 站位没校准、人太小（人高 < 0.30）；
3. 走的是掩码兜底链路而非姿态（看 `visionSource`）。

### 4.3 回答 Q3：`0.5` 系数 / `bodyScale` 公式要不要调？

**建议：`0.5` 与 `bodyScale` 公式都不改。** 依据：

| 候选改动 | 数据裁决 |
|---|---|
| 下调 `0.5`（如 0.35） | **反对**。表 2-4：门限是姿态关键点抖动的唯一防线；`ea=0.045` 的跳绳在 j≈0.013 就穿透，下调会直接吃安全垫 → 最小幅度动作出现"静止也计数"回归。 |
| 上调 `0.5`（如 0.6） | **反对**。表 2-3：开合跳在 k=2.6 已只有 1.28× 余量，上调会把真动作挡掉 —— 正是要避免的失败方向。 |
| 改 `bodyScale` 上限（1.5） | **不必**。实测人高最大 0.86（k=1），`H/0.6` 最大 1.43 < 1.5，上限没触顶。 |
| **改 `bodyScale` 下限（1.0 → ~0.6）** | **可选、低风险**。这是唯一能消掉"开合跳在远站位被挡"的方向，且不碰抖动防线。 |

**可选调整（若你希望为"孩子站得比推荐距离更远"留余量）：**

```js
// motion-engine.js detectReps()，仅把下限 1.0 改为 0.6：
const bodyScale = clamp((live.height || 0.6) / 0.6, 0.6, 1.5);
```

- 支撑：开合跳在 k=3.4（人高 0.227）时，`bodyScale` 由 1.0→0.6，门限 0.090→0.054，信号 0.079 → 信号/门限 **0.88×→1.46×**，由"挡"变"过"。
- 安全性：该改动不放行静止噪声 —— 姿态抖动地板（峰峰 ≈0.035，对应 j≈0.013）仍 **低于** 0.054；也就是"远距离真人静止"仍会被挡住。
- 代价：`bodyScale` 下限 1.0 是**为掩码链路**选的（掩码噪声地板不随人变小而缩小，故不能下缩）。姿态链路的噪声是**关键点抖动**、量级固定，因此对姿态链路放宽下限是安全的。若两条链路共用同一公式，需确认掩码链路的"4m 静止噪声"仍被挡（项目既有回放实验用的是 `clamp(h/0.6, 0.5, 1.5)`，见 `build/_exp-replay.js:87`，即 0.5 —— 与本次建议一致）。

**若你只想动一个数、不碰公式**，另一个等效选项是把 `data/fitness-plan.js:78` 开合跳的 `expectedAmplitude` **0.18 → ~0.12**：门限由 0.090→0.060（bodyScale=1 时），k=3.4 时 0.079/0.060=1.32× 通过；同时更贴合"真人标准开合跳 width 峰峰≈0.28、门限应取其一半"的设计口径。**但注意此字段同时驱动幅度评分**（`amplitude()`），下调会让幅度分更容易满分 —— 两职责需一起权衡。

**推荐优先做 4.3 的 `bodyScale` 下限调整（一处、只影响计次门限、不碰评分），而非改 `expectedAmplitude`。**

### 4.4 给「验收断言」的提醒（不改生产文件）

`build/motion-browser-test.js` 走的是**掩码链路 + 合成人形**（"数到约 9 次"用的是合成方块人，MediaPipe 对它返回 0 点 → 自动退回掩码）。**本次标定不影响它**：两条链路各自成立，姿态链路的测量结论不依赖也不改动那条断言。若后续把 4.3 的下限调整落地，务必确认掩码链路那条断言仍过（既有回放实验已在 `0.5` 下限上验证过）。

## 5. 证据强度自评

| 结论 | 强度 | 性质 |
|---|---|---|
| 姿态链路 `width/height/centroidY` 绝对值与波动（表 2-1） | **高** | 实测：真实动作视频 + 真实 MediaPipe + 生产同款映射，检 100%/92% |
| 现有门限下真实动作全部通过（表 2-2、2-5） | **高** | 实测：真实引擎端到端，被挡帧 0/408~413 |
| 姿态 `width` ≈1.9× 掩码（§3.1） | **中** | 两链路数据来自不同主体/画幅（掩码=受控合成人形@视距，姿态=真人宣传素材），比值量级可信、"姿态不更小"的定性判断可信，精确倍数有不确定性 |
| 门限对姿态抖动有 3~8 倍余量（表 2-4） | **中~高** | 实测（合成确定性抖动 + 真实引擎）；抖动模型是均匀分布，与 MediaPipe 真实抖动谱不完全相同，但量级远超实测抖动 0.002~0.006，结论稳健 |
| "正常站位不会挡真动作、开合跳远站位才会挡"（表 2-3） | **高** | 实测距离扫描 |
| `bodyScale` 下限调到 0.6 安全（§4.3） | **中~高** | 由表 2-3 + 表 2-4 联合推断：信号余量与抖动地板两头都验过；未在真机真孩子上验证 |
| 掩码链路在真实动作视频上无可比数据（§3.3） | **高（负面）** | 实测：引擎掩码链路 `width` 恒 0；已改用受控合成数据作两链路对照 |
| "开合跳幅度评分与计次门限存在双职责张力" | **推断** | 由 `fitness-plan.js` 注释 + `amplitude()` 代码读出：`expectedAmplitude=0.18` 同时喂幅度评分与计次门限，而实测真人标准开合跳 width 峰峰≈0.28 与门限 0.116 的关系，两职责的最优取值可能不同；未做评分端到端 |

**未验证 / 遗留：**
1. **真机真孩子**未测：本报告用的是真人**成人示范视频**（动作标准、画幅受控）。儿童做小幅度开合跳、房间光照/背景的真实影响未覆盖。建议真机跑一次，看 `window.__motionDebug().repSpread / repGate` 的比值是否稳定 > 1。
2. **宣传素材的掩码链路**不可用（§3.3），两链路比值只能算"中"强度。
3. 姿态链路 `reps` 的绝对数（表 2-5）受"7s 循环重放 + 视频本身节奏"影响，**只用于验证"门限放行"，不作为计数准确度验收**；计数准确度应由 `build/motion-browser-test.js`（掩码链路）与真机验收各自负责。
