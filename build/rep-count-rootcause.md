## 0. 结论摘要

**用户的反馈属实，你（team-lead）定位的根因方向也是对的，但需要一处关键修正和一个补充。**

1. **根因确认**：`motion-engine.js` 的 `detectReps()` 里，**没有任何"幅度绝对值"门限**。第 **2551 行** `const k = clamp(rms * 0.85, 0.45, 2.2)` 的阈值 `k` 完全由信号自身的 RMS 推导，而第 **2520 行** `detrend()` 又已经用整段标准差 `gstd` 把信号归一化过。两者叠加 → **幅度信息被彻底抹除**，任何微小噪声都必然穿越阈值。这是"不动也计数"的**直接原因**。

2. **修正你的假设 #3/#4**：`width` 信号本身**没有问题**，`minRepGap` 也不是根因（它只是把乱计数的速率**封顶**在 ~133 次/分，不是产生计数）。真正的机制是：**「完全静止」（零噪声）确实数 0 次；但只要有一点点亚像素传感器噪声（真实摄像头 100% 存在），就立刻开始稳定虚增**——0.6px 抖动 → 90 次/分，1.2px → 125 次/分。这正是孩子的真人场景。

3. **补充根因**：`expectedAmplitude` 这个"相对参考幅度"**从未参与计次**（确认你 #2 的判断，全库只有 `DEFAULT_PROFILE:128` 和 `amplitude() 评分:458` 两处），所以引擎没有任何"尺度无关的幅度基准"可用——修复必须把它接进计次路径。

4. **修复可行且可做到最小改动**：只需改 `detectReps()` 内部，加一个**基于原始（未归一化）信号 + `expectedAmplitude` + 人形尺度归一**的绝对幅度门。回放实验证明：该改动能让**全部 9 个场景**同时正确（静止噪声全部 0 次；大幅动作照数；回归测试的半蹲 0.6Hz 仍数 9~10 次）。

## 1. 根因判定（逐行）

### 1.1 主因：归一化 + 自适应阈值 = 幅度信息被抹除

**第 2504–2522 行 `detrend()`**：

```js
function detrend(raw, win) {
  // ...
  const gstd = Math.sqrt(gvar / raw.length) || 1e-6;   // 2512：整段标准差
  for (let i = 0; i < raw.length; i++) {
    // ... 减局部均值 m ...
    out[i] = (raw[i] - m) / gstd;                       // 2520：除以 gstd ★根因★
  }
  return out;
}
```

**第 2549–2551 行**：

```js
const d = smooth(detrend(raw, win), smoothK);           // 2549：d 已被归一化
const rms = Math.sqrt(mean(d.map(v => v * v))) || 1;    // 2550：用 d 自己算 RMS
const k = clamp(rms * 0.85, 0.45, 2.2);                 // 2551：阈值也是自适应的 ★根因★
```

**第 2557–2566 行的过零判定**，用的就是这个 `k`：

```js
if (v < -k) st.armed = true;
else if (v > k && st.armed) { /* 计数 */ }
```

**数学结论（可证明）**：设原始信号为 `x[i] = A·s[i] + b`（`s` 是归一化形状，`A` 是幅度）。则
`out[i] ≈ A·(s[i] - s̄)/gstd`，其中 `gstd ≈ A·std(s)`，于是 `out[i] ≈ (s[i]-s̄)/std(s)`——**与 A 无关**。
`rms(out)` 也因此与 `A` 无关。所以阈值 `k` 与 `A` 无关，判定结果与 `A` 无关。
**推论：无论振幅是 0.004 还是 0.4，输出完全一样。**（第 3 节有数值证据。）

唯一的"绝对兜底"是 `k` 的下界 `0.45`（`clamp` 下限）。但要让噪声的归一化值**始终**低于 0.45，需要噪声的标准差相对整段标准差极小——而对一段纯噪声而言，它的归一化标准差**恒为 1**，`rms≈1`，`k≈0.85`，噪声照样穿越。**这个下限对纯噪声完全无效**（只对"信号里混了一点噪声"有效）。

### 1.2 关键澄清：「完全静止」不计数，「静止+哪怕一点噪声」才计数

这一点必须说清楚，否则修复方向会跑偏：

- 我把真实引擎（`file://` + 真实 `motion-engine.js` + 合成人形）跑起来，喂**完全冻结、逐帧像素级一致**的人形 → **计数 = 0，正确**。
- 同样的静止人形，只加 **±0.6px 亚像素抖动**（矩形绘制位置 ±0.6px 取整波动），完全等价于真实摄像头传感器噪声 → **12 秒内计数 18 次（90 次/分）**。

**为什么冻结是 0**：`detrend` 输出恒为 0（`raw` 是常数），`v` 永远不越过 `k`。
**为什么 0.6px 就爆**：0.6px 的取整抖动让 `width` 在 {0.2813, 0.2917, 0.3125} 之间跳（量化台阶 1/96≈0.0104），相对 gstd 不算小；归一化后立刻变成 ±1 量级的方波，稳定穿越 `k≈0.85`。

**这就是为什么用户会看到"我做不做动作都在计数"**——真人站在镜头前，画面的像素抖动**不可能为零**（传感器噪声 + 视频压缩 + 自动曝光 + 背景掩码的量化）。冻结画面只是实验室理想态。

### 1.3 次因：`expectedAmplitude` 从未接进计次（确认你的 #2）

`grep -n "expectedAmplitude" motion-engine.js` 只有三处：

| 行号 | 位置 | 用途 |
|---|---|---|
| 128 | `DEFAULT_PROFILE` | 默认值 0.1，**从来没被读**（除了 458） |
| 458 | `amplitude()` | 评分用：`clamp(range / ref, 0, 1.6) / 1.6`，只影响"幅度分" |
| 3001 | 文档注释 | 无代码作用 |

`detectReps()`（2537–2570）**从未读取 `cfg("expectedAmplitude")`**。你的判断完全正确。

后果：引擎里**没有任何"这个动作做满应该是多大"的绝对基准**可用于计次判定。`amplitude()` 用 `expectedAmplitude` 是对的，但它只喂评分，不喂计数——于是"幅度不足"只会让孩子少拿分，**不会阻止计数**，这正好解释了用户"乱计分"的观感。

### 1.4 补充：`amplitude()` 也被同一套归一化间接伤害（次要）

第 454–460 行 `amplitude()` 用**原始** `signalWindow` 的 `range / expectedAmplitude`，本身是尺度正确的。但它是 `getState()` 里给 UI 的"幅度"读数（回归日志里 `幅度16%/29%`），与计次**完全解耦**。这意味着：**UI 显示"幅度不足"，计数却照样 +1**——两个子系统用了两套互不相干的幅度判断。这是"计次与幅度判断不一致"的代码级来源，修复时应让它们收敛到同一个门限。

## 4. 修复建议（最小改动）

### 4.1 核心思路

**在 `detectReps()` 内部加一道"绝对幅度门"，判定建立在 `detrend` 归一化之前的原始信号上，基准用 `expectedAmplitude`，并用当前人形尺度做距离归一。**

回答你提的两个设计问题：

- **归一化该放在门限判定之前还是之后？** → **门限必须建在原始（未归一化）信号上，在 `detrend` 之前/独立计算。** 现有 `detrend` 的归一化**保留不动**（它负责迟滞检测的手感），只是额外加一条与它并行的原始幅度判据。归一化不能"改好"，因为迟滞检测确实需要尺度无关的形状；缺的是**另一条独立的绝对幅度闸门**。
- **远距离（2~3m）绝对量级会变，门限不能写死像素值** → 用 `expectedAmplitude` 作"参考幅度"，再乘一个**只往上缩放**的尺度因子 `clamp(hBase/0.6, 1.0, 1.5)`，其中 `hBase` 是"人形高度慢基线"。近距离孩子大、信号大、门限相应抬高；远距离不降门限（避免噪声地板漏进来）。

### 4.2 最小补丁（**只改 `detectReps` 一个函数**，`detrend` 一行都不动）

在 `detectReps()`（2537 行起）内部插入约 12 行。**不需要**改 `detrend` 本身——它已经返回归一化结果；门限用 `raw` 单独算即可。下面是可直接落地的补丁草案（`motion-engine.js` 2537–2551 行一带）：

```js
function detectReps(now) {
  if (!profile || profile.mode !== "rep") return;
  const band = cfg("tempoBand") || [20, 60];
  const win = clamp(Math.round(fps * 60 / Math.max(15, band[1])), 3, Math.round(fps * 1.5));
  const smoothK = Math.max(1, Math.round(fps * 0.06));
  const minGap = cfg("minRepGap") || 0.5;

  /* ★新增 1：幅度门限的参考幅度（该动作"做满"时的典型波动范围） */
  const refAmp = cfg("expectedAmplitude") || 0.1;
  /* ★新增 2：人形尺度参考。站位校准时推荐"人占画面高 45%~75%"（evaluatePose:1499
   *   的 size 判据），取中值 0.6 作参照。只往上缩放：近处更严，远处不降门限，
   *   这样不会把远距离的恒定像素噪声地板放进计次。 */
  const bodyScale = clamp((live.height || 0.6) / 0.6, 1.0, 1.5);
  const gate = refAmp * 0.5 * bodyScale;      // 0.5 = 峰峰值需达到参考幅度的 50%

  signalList().forEach(key => {
    if (!repCounters[key]) repCounters[key] = { armed: false, lastAt: -1 };
    const st = repCounters[key];
    const raw = signalWindow(key, 3.5);
    if (raw.length < 10) return;

    /* ★新增 3：绝对幅度闸门 —— 原始信号（未归一化）的峰峰值 */
    const spread = Math.max(...raw) - Math.min(...raw);
    if (spread < gate) { st.armed = false; return; }   // 幅度不够 → 不计数，并清迟滞状态

    const d = smooth(detrend(raw, win), smoothK);
    const rms = Math.sqrt(mean(d.map(v => v * v))) || 1;
    const k = clamp(rms * 0.85, 0.45, 2.2);
    // ...（以下 2553–2569 行原样不动）
  });
  repTimes.sort((a, b) => a - b);
}
```

**改动要点**：
1. **不动** `detrend` / `smooth` / 过零迟滞的任何一行 —— 大幅动作的手感完全不变。
2. 门限建立在 **`raw`（未归一化）** 上 —— 这是恢复绝对幅度的关键，也是回答"归一化在前还是在后"的答案。
3. `spread < gate` 时 **`st.armed = false`** 并 `return` —— 防止"门限刚好卡在 armed=true 的瞬间"残留迟滞状态造成跨周期误计数。
4. 尺度因子 `bodyScale` **只往上缩（下限 1.0）** —— 回放扫描证明这是唯一两向都不出错的策略。
5. `0.5` 这个比例来自 `_exp-variant.js` 扫描：在 RATIO=0.5 时 9/9 场景正确（0.35~0.4 会在远距离漏噪声，0.6+ 会挡掉一些真动作）。

### 4.3 可选：让 UI 的"幅度"读数与计次门限同源

`amplitude()`（454–460）现在独立算幅度分。建议让它复用同一个 `gate`，这样"UI 说幅度不足"与"计数被门限挡住"就**同进同退**，不会再出现"幅度显示不足、计数却 +1"的矛盾（§1.4）。这是可选优化，不影响主修复。

## 5. 风险与回归影响

### 5.1 必须先确认的一个参数：回归测试的 `expectedAmplitude` 从哪来

`build/motion-browser-test.js:594` 的骨架几何测试用的是 `eng.setProfile({ mode: "rep", signal: "centroidY" })`——**没有传 `expectedAmplitude`** → `cfg()` 回退到 **`DEFAULT_PROFILE.expectedAmplitude = 0.1`**（`motion-engine.js:128`）。

而主流程（第 297–305 行选「半蹲热身」）走的是 `data/fitness-plan.js:62` 的真实 profile：`expectedAmplitude: 0.06`。
该测试喂的是「人形上下往复 12px / 画面高 96 ≈ 0.125」的合成运动，实测 `centroidY` 峰峰值约 0.09~0.22。

- 用 0.06：门限 = 0.06×0.5×scale(≈1.43) ≈ 0.043 → 远低于 0.09 → **计数照旧（回放实测 10 次）✅**
- 用 0.1：门限 = 0.1×0.5×1.43 ≈ 0.072 → 仍在 0.09 之下 → **计数照旧（回放实测 9~10 次）✅**

两种来源都能过。但**这是这条断言最脆的一环**：`0.6Hz × 15s ≈ 9 次` 的容差是 `4 ≤ reps ≤ 15`，而真实信号峰峰值 0.09 与门限 0.072 只差 25%。**建议把 `motion-browser-test.js` 合成人形的纵向摆幅从 12px 提到 16px**（让信号峰峰值到 0.12 以上），把这条断言从"擦边"变成"有余量"。这是**测试夹具的调整，不是引擎改动**。

## 6. 未能证实 / 遗留

1. **真实摄像头噪声量级未实测**：我的噪声是合成的（±0.6~2px 抖动）。真实摄像头的噪声统计（尤其自动曝光/自动对焦切换时）可能更大或更结构化。**建议在真实房间跑一次 §3.3 的探针**，用 `getState().live.width` 采样，确认真实噪声峰峰值落在门限下方。若真实噪声更大，`RATIO=0.5` 需要上调。
2. **「完全静止数 0」不代表"正确"**：由于 `minRepGap` 是唯一的限速器，一个"缓慢持续抖动"的真实物体（比如电风扇、飘动的窗帘）会让计数以 133 次/分封顶。绝对幅度门限修复了这一点（这类物体的 `width` 波动通常 < 0.05，会被挡下）。但**如果窗帘的波动幅度恰好超过门限**，仍会误计——这是背景差法的固有限制，非本次修复范围。
3. **§3.4 的"全幅开合跳"只到 0.083~0.115**，低于项目声明的 0.18。我无法用合成人形复现一个**真正达到 0.18 摆幅**的开合跳（128px 宽的画布、腿张开 22px、手臂外展 14px，bbox 只增加约 0.083）。**这不代表真实开合跳达不到 0.18**——真实孩子手臂完全上举时，MediaPipe 的 `width` 或掩码 bbox 会显著更大。建议用真机验证：让一个孩子做标准开合跳，记录 `live.width` 峰峰值，确认 ≥ 0.18×0.5。
4. **`detrend` 的第二个隐患**（未展开）：`gstd` 用整段算，若信号里混入一个**大毛刺**（比如孩子短暂走出画面导致 bbox 突变到 1.0，`E_squat06` 里就出现了 22 帧 `width>0.9`），`gstd` 会被拉大，导致正常动作的归一化幅度被压缩、**漏计数**。这是与"误计数"相反的失效方向。修复主因后建议顺手加一个**中位数/分位数限幅**（把 `raw` 里超过 P95 的样本截断）再算 `gstd`，但这属于**额外改进**，不是本次必需的。
